## What this project is

A learning project: build a "Story AI Assistant" RAG chatbot over a Vietnamese web-novel series (summarization, Q&A, plot explanation with citations, scene illustration). The owner is learning RAG while building, so the roadmap is [rag_story_ai_learning_plan.html](rag_story_ai_learning_plan.html) (8 modules, milestones V0–V6: Data → Basic RAG → Citation → Summary → Reasoning → Image → Final). It is a self-contained study tracker, not application code; its checklist state lives in the browser's localStorage.

Current state: **V0 (Data) and V1 (Basic RAG: Modules 03–04) are complete; V1 closed 2026-11-12.** Final V1 configuration (user decision): baseline hybrid-header / k=5 / no expansion / prompt v3, followed by the step-9 policy (cheap gate → one-shot repair loop → refuse when the second verification fails the scene check); query rewriting/splitting (Experiment B) is a **gated rescue only** — run it when the verdict is a refusal, never unconditionally (control Q08 showed unconditional rewriting hurts healthy queries). Accepted gap left for V2+: confidently-wrong answers with clean citations (the Q01-v2 type) pass every gate. Next milestone: V2 (Citation). Chunk parameters 1000/200 chars are locked only provisionally: revisit them with hit@k numbers from the V1 evaluation. V1 plan (agreed in outline): (1) embedding basics, (2) embed the 393 chunks into Chroma with and without `context_header` (two collections), (3) top-k retrieval, (4) metadata filter + prev/next neighbor expansion, (5) `answer()` pipeline with a printed trace, (6) small hit@k evaluation (~10 questions, some unanswerable), (7) wrap-up; BM25/hybrid only if dense retrieval is weak. **Embedding decision (2026-11-11): use the Gemini embedding API (option A), not local bge-m3.** The bge-m3 weights (~2.2GB) were judged too heavy: the download was started, aborted at ~244MB, and the partial weights deleted (only the small tokenizer files remain in the Hugging Face cache, still needed for `token_count`). **V1 Step 5 (`answer()` with trace) is done.** Code: `src/rag.py` (`RagPipeline.answer()`, `format_trace`, `verify`, `quote_match`; `GEMINI_MODEL`/`TRACES_DIR` in `src/config.py`; `rank_all_methods` now takes `where`/`allowed` for chapter filters and `parse_chapter_set`/`chapter_where` live in `src/retriever.py`) and `scripts/v1_step5_answer.py` (`--ask`, `--eval`, `--k`, `--expand`, `--max-context-tokens`, `--no-llm`, `--show-prompt`, `--save`; the question's own "chương N" auto-filters). Defaults: model gemini-3.5-flash-lite, method hybrid-header, k=5, expand 0, budget 6000 bge-m3 tokens, temperature 0, JSON output {verdict, answer, missing, citations[{chunk_id, paragraph, quote}]}. The trace separates three sets: retrieved (top-k, with rank/id/chapter/paragraph and dense/BM25 ranks), context candidates with a `sent` flag and `drop_reason`, and what was actually sent; budget rule = priority order (top-k first, then neighbors by parent rank), the first chunk that overflows and everything after is dropped and flagged `!!!` if it was a top-k chunk; real input tokens come from the API `usage_metadata` (about 1.5x the bge-m3 estimate once system prompt and paragraph numbers are counted). Traces (incl. full prompt) are saved under `data/traces/<run>/<qid>.json`. Prompt rules: only the provided passages, every claim cited `[chunk_id, chương X đoạn N]`, no guessing sources or motives, answer the part that is supported and name what is missing, otherwise "không đủ thông tin" (v3 adds: the cited passage must match ALL conditions of the question). Prompt versions: v1 chunk-level labels (model invented paragraph ranges, e.g. chunk đ1-7 labelled "đ8-10"); v2 numbered paragraphs `[đN]` so citations are paragraph-level and checkable; v3 adds the all-conditions rule. Verification checks cited ids are in the sent set, labels fall inside the chunk, and each quote against its own paragraph as exact / close (>=80% of word 4-grams) / other_para / none. Results on 21 questions (19 answerable + 2 not in story; H09 skipped as duplicate), answers graded by reading them against `expected_answer` (Claude's reading, user should spot-check): v1 k5 = 17 correct, Q07 partial (honest), Q01 honest refusal, 2 wrong paragraph labels; v2 k5 = 17 correct, Q07 partial, **Q01 confidently wrong**; v3 k5 = 16 correct, Q07 partial, Q01 honest refusal (stable 4/4 reruns), Q09 refused; v3 k10+expand1 = 17 correct, Q07 partial (other half), Q01 refusal, 1 label error; v3 k5+expand1 = 17 correct, Q07 partial, **Q01 confidently wrong again** ("đoạn cuối truyện (chương 59)"). All configurations land at 16–17/19, i.e. within noise; what differs is the failure mode. Findings: (1) quote verification proves a quote EXISTS, not that it answers the question: Q01's wrong answers had 2/2 exact quotes from a different scene (ch59) because the true chunk was never retrieved (rank 25), and prompt rule 6 did not make this reliable (2 of 5 configs still wrong); score thresholds cannot catch it either. (2) Q09: with k=5 the sent chunk c075-k03 (đ30-41) lacked đ29 (the only paragraph saying Lãnh Duệ handed over the book), so v3 correctly refused; `--expand 1` adds c075-k02 and fixes it. (4) More context also broadens answers (H05 at k=10+e1 added a different cheque from ch7). (5) Q07 (two evidence pieces in different chapters) is always answered only half.

Causes of the missing evidence: Q01 dense-header rank 3 but BM25 rank 178, so RRF fusion pushed hybrid-header to 25 (natural wording without the book's vocabulary; no adjacency; dilution probe not yet measured, earlier plain-collection probe suggested Δ=+0.07); Q07 second fact (ch58/60/73) at hybrid rank 10 (dense 7, BM25 18), two facts in different chapters → split the question; Q09 is the only boundary case (retrieved c075-k03, needed đ29 lives in the adjacent c075-k02), 1 of 21 questions. So chunk boundary/length is NOT yet shown to be a real problem. **Free-tier quota discovery:** Gemini embedding allows 1000 embed requests per day per model (`embed_content_free_tier_requests`; apparently counted per text: Step 2 alone used 786); re-running the eval re-embedded the same questions each time and hit the limit, after which every embedding call fails with 429 "per day" for hours (the API said retry in ~5h16m; the generation model was not tested). Consequences: any NEW query vector (rewritten/split questions) and the dilution probe need quota; a smaller-chunk experiment would need >1000 embeddings (two variants of ~800+ chunks), so it must be spread over days or limited to one variant.

**Experiment A2 (small, 2026-11-12): one-shot repair loop** (`scripts/v1_step8_repair_loop.py`, `src/verifier.py`, `RagPipeline.answer_from_chunks`). Flow fixed by the user: saved answer → verifier → "giữ" keep | "sửa từ bằng chứng hiện có" re-answer from the same chunks with the verifier's notes | "cần tìm thêm" add ±1 neighbor chunks (by stored ids, no embedding) and re-answer → verify again → STOP even if information is still missing. Each case saves before/after answers, the verifier's reason, added chunks, evidence/citation flags graded against the gold (never shown to the LLM), and extra tokens/seconds (`data/traces/repair-<time>/`). Controls: 3 already-correct answers left to the verifier (all kept) plus 4 correct answers FORCED through the "add neighbors → re-answer" branch (Q04, Q08, H02, H10: all stayed correct, wording only). Results: **Q09** refusal → correct in 5 of 7 loop runs, 1 run correct plus an accurate extra sentence (Lãnh Duệ "brought" the book Đường Quả wrote, ch77), 1 run with a WRONG extra claim (that Lãnh Duệ gave her the tragic novel; the cited ch77 đ11-12/19 say he asked why she wrote it; she, not he, is the author) which the second verification passed ("giữ"); **Q07** the verifier's first action varied across identical inputs (6 samples incl. Step 7: "sửa" 4×, "cần tìm thêm" 2×); on the "sửa" route the re-answer was complete and correct (3/3, citing ch75 đ11), on the "cần tìm thêm" route neighbors were added but the answer stayed partial (2/2); **H03** citation addresses fixed (1 exact + 2 other_para → 3 exact) but the omitted smile (ch1 đ17) still missing; **Q01** (both traces) neighbors did not help, the answer stayed the same wrong ch59 scene and the second verification flagged scene "không đạt"/"cần tìm thêm", so stopping leaves a wrong answer in place unless the final policy abstains; **H01** kept (verifier miss). Cost (first full run, 13 cases): +111.7k tokens (3.1x the original passes) and +113s; per case: verifier alone +2.7–2.9k tokens (~+100% of a normal answer) and ~+2s, "sửa" path +9.3k, "cần tìm thêm" path +8.5–14.6k (3–5x), with 35–37s outliers on two cases. Findings: (1) the loop helps when the missing information is already sent or adjacent (Q09, Q07 on the "sửa" route) and for citation addresses; (2) it cannot fix wrong-scene answers caused by retrieval misses (Q01); (3) verifier routing is not deterministic even at temperature 0, so the outcome depends on which action is sampled; (4) the verifier is not a safe final gate: it passed Q09's wrong extra claim (1 of 7) and the repair can introduce a new error while fixing the old one; (5) the extra cost is largely the verification of answers that are already fine. Proposed final policy (derived from saved results, not yet run live): after the single repair, if the second verification says scene "không đạt", replace the answer by "không đủ thông tin" (triggers only on the two Q01 traces among the 13 cases); gate the loop with cheap triggers (verdict other than "đủ", or deterministic citation flags such as other_para/none) instead of verifying every answer, noting this would not catch confident-wrong answers with clean citations like Q01-v2. Sample sizes are tiny (7 loop runs for Q09, 5 for Q07, 4 forced controls); treat as exploratory.

**Experiment A3 (2026-11-12): policy (a) = cheap gate + one-shot repair + final policy** (`src/repair.py`, `scripts/v1_step9_policy_eval.py`; verifier v2 adds `Claim.fits_question`). Policy as the user corrected it: only answers with verdict ≠ "đủ" or deterministic citation flags (other_para / none / bad label / cited-not-sent) go through the verifier; then verify → keep | re-answer from the sent chunks with the verifier's notes | add ±1 neighbors and re-answer → verify again → stop; final policy on the last verification: drop claims that are unsupported or do not fit the question's scene (if the scene is "không đạt" and no claim is flagged, treat all claims as not fitting); if no claim is left, answer "không đủ thông tin". **Stated limit: the policy only protects answers that pass through the verifier.** Results on the 21 baseline answers: the gate fires on 6/21 (H03, Q01, Q07, Q09, U1, U2); not fired but not correct: H01 and both confidently-wrong Q01 traces (Q01-v2, Q01-k5e1: verdict "đủ", clean citations) → NOT protected. Triggered cases, 3 runs each: Q09 refusal → correct 3/3 (neighbors added); H03 citation addresses fixed 3/3 (3 exact quotes, no bad labels) but the omitted smile (ch1 đ17) still missing; Q07 mixed: 1/3 complete and correct (ch75 đ11), 1/3 unchanged partial (verifier said "giữ"), 1/3 a NEW flawed claim ("nàng trở thành mẹ kế (bà bà) của Lãnh Tử Việt" citing ch75 đ3, which is Lục Kỳ's thought) that the second verification passed; the flaw was inherited from the verifier's first notes (it had listed only đ3), so verifier mistakes propagate through the feedback; Q01 (baseline answer was an honest refusal): the repair produced a confident wrong ch59 answer 3/3 and the final policy turned it back into a refusal 3/3 (final = baseline, but +12.4k tokens for no gain); U1/U2 (correct refusals) stayed refusals 6/6, but U1 cost ~11.4k tokens per run. Forced through the verifier although outside the gate: Q01-v2 refused 2/2, Q01-k5e1 refused 1/2 and kept the wrong answer 1/2 (second verifier said scene "đạt"). Controls (6 already-correct answers forced through verifier + final policy): all kept unchanged, no false trimming or refusal. Overall for engaged wrong-scene answers the final policy refused 6/7. Verifier routing stayed unstable (Q07 first action: giữ/sửa/sửa; U2: cần tìm thêm/giữ/giữ). Cost on the 21 baseline answers: 55.7k tokens / 51s for the original answers; the policy added on average 57.5k tokens / 87s (only 6 answers pass the gate) → 2.03x tokens; about half of the extra tokens (~29k: Q01, U1, U2) went to cases whose final answer equals the baseline. Net benefit measured so far: Q09 fixed, H03 addresses fixed, Q07 a coin flip with a 1/3 risk of a new error, nothing for ungated errors. Not yet tested: gating refusals by a cheap lexical signal (e.g. BM25 score of the retrieved chunks' neighbors), dropping or verifying the verifier's omissions before using them as feedback. ## Stack decisions

Agreed: **Python only. No low-code tools (Langflow dropped) and no frameworks such as LangChain/LlamaIndex**; use core libraries directly (`chromadb`, `google-genai`). Gemini API for both the LLM and embeddings, Chroma as local VectorDB. The demo UI at V6 is **Streamlit**. The pipeline visibility Langflow would have given is replaced by printing a trace per query (retrieved chunks, similarity scores, final prompt). Image generation is decided at V5 (Gemini image model vs local diffusion on the M5/24GB Mac). Embeddings: Gemini embedding API (decided 2026-11-11, see below); comparing against a local model such as bge-m3 is optional extension practice. The learning plan HTML was updated to match (stack table, checklist, Module 08, V6).

Gemini model availability (checked 2026-11-10): the `gemini-2.5-*` models list as available but return 404 "no longer available to new users"; `gemini-3.8-flash` returned 503 (high demand); `gemini-3.5-flash-lite` works and is the default in `scripts/step1_why_rag.py` (override with the `GEMINI_MODEL` env var). The SDK retries slowly on 503, so wrap calls in a short timeout. Image-capable models seen in the model list include `gemini-3.1-flash-image` and `gemini-3-pro-image` (relevant for V5).

Decided: experiments are `.py` scripts in `scripts/` that print to the terminal (not notebooks); reusable code lives in `src/`; the chunker was hand-written (no LangChain splitter comparison); chunk sizes are in characters for now.

Chunk metadata and token counting (decided in Step 5): `token_count` is computed with the `BAAI/bge-m3` tokenizer (recorded per record in `tokenizer`) on the exact embedding input `context_header + "\n\n" + text` (use `embed_input()` everywhere), with special tokens included (+2: `<s>`, `</s>`) and `truncation=False`, so over-long inputs are detected against the model limit of 8192 tokens instead of being silently cut. `context_header` is stored separately from `text` so V1 can A/B embedding with and without it. `prev_id/next_id` chain all chunks of a world in reading order, across chapter boundaries. Measured on World 01 (1000/200 chars): 393 chunks, 107–366 tokens (mean 262), about 3.3 characters per token, none near the limit. Only the bge-m3 tokenizer files are kept, not the ~2GB model weights. Since embeddings now come from Gemini, `token_count` is only an approximation of Gemini's own tokenization (not measured); it is still useful for spotting over-long chunks.

Gemini embedding (decided 2026-11-11, user approved): the user accepted that the full World 01 text (393 chunks, ~306k chars) is uploaded to Google for embedding, despite the free-tier data-use concern; only World 01 is ever sent (see Scope). Facts verified against the API with the user's key:

- Two embedding models are available: `gemini-embedding-001` (input limit 2048 tokens) and `gemini-embedding-2` (8192). Both return 3072-dim vectors with norm 1.000. **Use `gemini-embedding-001` for Step 2**: it takes a batch (one vector per text) and honors `task_type` (`RETRIEVAL_DOCUMENT` for chunks, `RETRIEVAL_QUERY` for questions, `SEMANTIC_SIMILARITY` for symmetric comparison).
- `gemini-embedding-2` **merges a list of `contents` into ONE vector** (silent failure if you batch) and **ignores `task_type`** (cosine with/without it = 1.0), so it must be called one text at a time. It did not beat `-001` on the Step 1 experiments. `embed()` in `scripts/v1_step1_gemini_embedding.py` handles both and checks the returned vector count.
- Scores are compressed: cosine sits roughly in 0.5–0.85 (an unrelated sentence pair scored 0.74, a near-paraphrase 0.975). Do not use absolute thresholds like "> 0.8"; rely on top-k ranking or calibrate a threshold from data (matters for "not in the story" questions).
- Step 1 experiment result: question about the pen (Q2) retrieved the right passage by a wide margin (0.852 vs ≤0.60), but "What is Đường Quả holding?" (Q1) retrieved the pen passage (names "Đường Quả", "hai tay") instead of the milk-tea passage that only says "nữ hài" (the girl), with both models. Hypothesis (unverified): the character name outweighs meaning. This supports testing neighbor expansion, an alias glossary and hybrid BM25 in V1. A convert-vs-natural wording test showed almost no penalty on that one sentence (0.737 vs 0.740, control 0.632).

## Data: the corpus is `Books/Truyen/` only

- 20 files `NN - Title.txt` (NN = 01–20), UTF-8. Each file is one self-contained "world" of a *xuyên nhanh* (quick transmigration) series; the protagonist "Đường Quả" recurs across all worlds. Totals: **1,542 chapters, ~1.3M words** (chapters are short, ~800 words; 55–122 chapters per world).
- Hierarchy to preserve: Series → World → Chapter → Chunk. This enables hierarchical summaries (chapter → world → series) and cross-world questions via metadata filtering.
- File format: line 1 = title, line 2 = `=====`. Each chapter starts with a heading line like `12 phú thiếu bạn gái cũ ( 12 )` followed by a `-----` underline; the last chapter reads `( xong )`. Detect headings as "non-empty line followed by a line of 5+ dashes" (verified on all 20 files). Chapter titles repeat the world title, so citations must use numbers, e.g. "Thế giới 1 – Phú thiếu bạn gái cũ, chương 12". Chunks must never cross a chapter boundary.
- Planned chunk metadata (for citations in V2, neighbor expansion in V4, filtering by world): `chunk_id, world_no, world_title, chapter_no, chunk_index, para_start, para_end, token_count, prev_id, next_id, text`, written as JSONL to `data/chunks/` (git-ignored).
- **Scope (decided): the whole training course (V0–V6) uses World 01 only** (81 chapters, ~67k words, 393 chunks at 1000/200). Do not chunk, embed, or test on the other 19 worlds in `Books/Truyen/`; they are reserved as extension practice after the course is finished. Consequences: the "run the loader/chunker on all 20 worlds" backlog item is dropped, cross-world questions and the world-level layer of hierarchical summaries are out of scope during the course, and the code should stay world-agnostic (e.g. `world_no` parameter) so extending later needs no rewrite.
- Text quality: the text is raw machine "convert" style from Chinese (Hán-Việt vocabulary and Chinese syntax, e.g. "nữ hài", "hảo", "ngươi/ta"), not natural Vietnamese. Expect vocabulary mismatch between natural questions and the text; test with both natural phrasing and the book's own vocabulary, and note that character names are strong retrieval anchors.
- The corpus is copyrighted web-novel content: personal learning use only; don't commit `Books/` or generated data to a public repo.
- Gemini is unlikely to know this text from pretraining (unlike famous books), so answers can be judged as grounded in retrieval. Still include "not in the story" questions in evaluation (V2+).
- Out of scope: `Books/Xuyen_nhanh_nu_xung_cac_truyen_hoan_thanh/` (the original 50 worlds plus 3 `Chuong_trong_dan` group-chat interludes, whose chapter numbers 3875+ suggest they belong to later worlds) and `Books/Harry Potter/` (two parallel EN/VI editions of book 1, `.mobi` plus generated `.txt`, 17 chapters each; abandoned as corpus because Gemini already memorized it). Don't read from them unless the user asks.
